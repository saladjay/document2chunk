## 1. 线上实证:unhealthy 是结构性误报(2026-09-17 判定)

**判定:业务完全正常,unhealthy 为探针结构性误报,不是故障。**

| 证据 | 读数 | 含义 |
|---|---|---|
| 近 5 分钟业务 | 6× POST /parse-pdf 全部 200 OK | Chai 投喂的每个文档都成功解析返回 |
| CPU | 100.1%(单核慢跑解析) | 正在干活,不是卡死 |
| 内存 | 1.2GiB / 4GiB | 无泄漏,非 OOM(OOMKilled=false, RestartCount=0) |
| healthcheck 日志 | 连续 5 次 `[-1] exceeded timeout (5s)` | 真相所在 |

**机制**:healthcheck 超时仅 5s,而 Chai 持续投喂时事件循环几乎总被解析占着(P0-1)——每次探测都落在解析窗口里,5s 等不到响应 → 连续失败 → 翻 unhealthy。服务一直在正确处理业务:同步解析阻塞事件循环 + 密集流量 = healthcheck 永远探不进去。

**当前影响与实际风险**:unhealthy 目前只影响观感(compose 的 `unless-stopped` 不会因 unhealthy 自动重启容器);但任何基于 unhealthy 做自动重启的监控/脚本,会在解析中途杀容器,直接弄死 Chai 正在等的解析任务。

**两个处置(可并行)**:

1. **止血(监控/运维侧)**:禁止任何自动重启逻辑以裸 unhealthy 为触发条件。要报警就用双条件:「业务请求持续零 200 + CPU 空闲」才是真故障;unhealthy 且 CPU 单核满转 = 正在干活。`unless-stopped` 保持现状。
2. **根治(代码侧)**:落实 P0-1——解析移出事件循环(端点改 `def` 走线程池或 `run_in_executor`)。解析不再占事件循环后,`/health` 随时可响应,误报自然消失。单纯调大 healthcheck 超时不解决问题:持续投喂下解析窗口可超过任意超时值。

**判别口诀**:先看业务码与 CPU,再看 healthcheck——unhealthy + CPU 满转 = 干活;unhealthy + CPU 空闲 + 业务零 200 = 真死,才需要重启。

## 2. P0 — 服务级致命(大文件必触发)

### P0-1 ✅ 整个解析同步阻塞在事件循环上,单 worker 无并发

- `api.py:351` 起所有端点均为 `async def`,但核心工作全是同步调用直接跑在事件循环:`api.py:377`(`parse_to_files`)、`api.py:392`(`parse_to_zip`)、`api.py:436-449`(`/parse-json` 同步 `parse`)。全库无 `to_thread`/`run_in_executor`。
- 下游同步阻塞叠加:OCR 同步 `httpx.Client` + `time.sleep` 指数退避(`ocr/_client.py:92,54`)、表格服务 `sleep(5)` 重试(`table/_client.py:86`)、soffice 最长 120s(`legacy_convert.py:69-75`)。
- **后果**:一个 143MB 文件解析期间(分钟级),整个服务含 `/health` 全部无响应;这正是第 1 节 unhealthy 误报的根因。
- 对照组:mineru2doc 端点用普通 `def`(FastAPI 自动进线程池,`mineru2doc/server.py:61`),无此问题。

### P0-2 MuPDF 挂死无看门狗 → 唯一 worker 永久卡死

- 毒 PDF 的保护手段(faulthandler / subprocess timeout)**只存在于 `_forensics/` 取证脚本**(`triage.py:49-56` 等),生产链路零保护;`src/` 内 grep `faulthandler|signal|SIGALRM` 仅命中 `legacy_convert.py:78`(soffice 杀树)。
- 叠加 P0-1:一个 killer.pdf(`_forensics/killer.pdf`,7.2MB)进来,单 worker 服务永久瘫痪,只能重启容器(参考 [[d2c-112-ops]] 故障模式 3:实测烧 CPU 5h)。

### P0-3 ✅ 全链路整读进内存,无流式、无大小上限

- 上传整读:`await upload.read()`(`api.py:388,478`)、`await request.body()`(`api.py:412,480`)。
- 结果内存拼 zip 整体返回:`serve.py:399-425`(BytesIO + `getvalue()`);`/parse-json` 双重序列化 `json.loads(doc.model_dump_json(exclude_none=True))`(`api.py:455`)。
- `/parse` 代理链 = d2c 整读 → 整体转发 → mineru2doc 整读(`mineru2doc/server.py:113`)→ 整包 zip 回传 → 整包再回传客户端,全程无流式。
- **143MB DOCX 峰值放大(见 P1-5)后,4G 容器约 1-2 个并发大请求即 OOM**。

### P0-4 ✅ OCR 串行逐页 + 失败全弃

- N 页扫描件 = **N 个串行 HTTP 请求**(`ocr/extractor.py:83-85`,for 循环内同步 `self._client.parse`);每请求新建 `httpx.Client` 无连接复用(`ocr/_client.py:92-93`);单页超时 300s × 3 次重试。
- 500 页文档最坏理论耗时 ~500×300s,远超客户端 30 分钟读超时上限。
- **失败放大**:第 399 页失败即抛 `OcrServiceError`——它不是 `Document2ChunkError` 子类,不在 `serve.py:348` 老格式兜底范围,直通 500,**前 398 页成功结果全部作废**。
- 背景:按页切分本身是正确设计(`ocr/_chunker.py` 注释:整份送 unlimited-ocr 实测 49 页即 500),缺的是并发、连接复用与部分结果保留。

## 3. P1 — 大文件超线性开销(重复劳动与 O(n²))

### P1-1 ✅ 同一文档反复打开 / 重复扫描(PDF 路)

- `detect_pdf_type` **每请求跑 2 遍**:路由层 `api.py:214` + 提取器内部(`pdf.py:585` 默认 `skip_detect=False`,`serve.py` 从不传该参数)。每遍全文档逐页 `get_text("dict")` + `get_image_info`(`pdf_detect.py:78-104`)。
- ✅ `serve.py:224-231`:OCR 路为取页面宽高**白跑一遍 `iter_pages`**(每页 `insert_pdf`+save 构造单页 PDF 并序列化),`geo` 在两个调用点(`serve.py:332,402`)接收后**从未使用**;真正提取时再完整跑第二遍 → 每页被切分/序列化 2 次。
- editable 路一次请求约 **5 次整档解析**:detect×2 + `_open_pymupdf`(`pdf.py:211`)+ pdfplumber(`pdf.py:268`)+ serve 几何(`serve.py:244`)。
- 表格截图模式再乘:每页重新 `fitz.open`(`_table_image.py:42-44,170-172`)。

### P1-2 DOCX 链路的重复解压与重复扫描

- ✅ `package_reader.py:89` `media_info_for_rel` **每次调用重新 read_bytes + 重新解析 rels XML + 整图解压**,无任何缓存;`media_for_rel`(`:79-86`)直通它。N 张图 ≈ 3N 次 rels 解析 + 3N 次图片解压(解析期 1 次 + 合成期背景/前景各 1 次 + 落盘期 1 次)。
- ✅ 解析期拿整图 bytes 只为取扩展名:`parser.py:513` `_, fmt = media`,bytes 即弃。
- 每段落重复劳动:`find(w("pPr"))` 最多 5 处(`parser.py:146,273,323,357,690`);TOC 域判定每段全子树 `iter`(`parser.py:134,673`);每段 2-3 次全子树扫描 + 每元素祖先链回溯到根(`parser.py:462-467,540`、`embedded.py:64-71`);`_heading_level_source` 同一段落算两遍(`parser.py:145-152`)。
- 样式继承链每段重建、无缓存(`parser.py:376` → `styles.py:127-157`)。
- 整树常驻:document.xml 全树 + styles + numbering 同时持有(`extractor.py:304-317`),全模块无 `iterparse`/流式解析;143MB DOCX 的 lxml 树通常 5-10 倍膨胀(数百 MB),是 4G 上限下最先爆的路径。

### P1-3 O(n²)/超线性热点

| 位置 | 模式 |
|---|---|
| `pipeline/stages/classification.py:63-77` → `heading_scorer.py:64-77` | `is_standalone_line` 每元素扫同页全部元素,**页内 O(n²)** |
| `postprocess.py:304-349` | 页码检测:每个候选块扫**全文档**块列表 O(候选×全文块) |
| `pipeline/stages/image_detection.py:194-199,258-261` | O(图×元素) + 页内图片两两求交 O(图²) |
| `pipeline/stages/merge.py:73-74` | 段落合并 `text = text + elem` 同段每并一行重建整串,单段 O(L²) |
| `pdf.py:445-463` | `_reorder_overlapping` 冒泡带回退,最坏 O(n²) |
| `pdf.py:359` | 每条文本行 × 全部表格 bbox 重叠检测 O(行×表) |

### P1-4 内存冗余副本贯穿全程

- pipeline element 同一份文本存 3 份:`"text"` / `"markdown"`(同为全文)/ `"spans[]"`(每 span 再一份)(`pdf.py:387-409`),映射成 BlockNode 后才释放。
- IR 每块 `text` + `runs` 双份存同一文本(`ir/models.py:106-109`;OCR 路 `ocr/_mapping.py:319`;表格 geo 路 `_geo_reconstruct.py:328-331`)。
- docx 合成图:RGBA 解码 + LANCZOS resize + PNG 重编码,bytes 进 `ImageNode.data`(`extractor.py:198-270`),再被 `/parse-json` base64 化(`api.py:455`,`exclude_none` 不排除非 None bytes)。
- `_save_zip_artifacts` 开启时同一内容内存+磁盘最多 3 份(request.bin + response.zip + 解包),**无清理/轮转**(`serve.py:51-77`)。
- `format_detect` 单次识别路径 3-4 份整 bytes 拷贝(`format_detect.py:74-148`)。

### P1-5 DOCX 大文件峰值估算(143MB 样本)

zip 原文常驻(BytesIO,`package_reader.py:18-22`)→ document.xml lxml 全树(数百 MB)→ 图片多轮解压 + PIL 合成(每张原始 bytes×3 轮)→ 合成 PNG 常驻 IR → markdown/JSON 全文串 → 内存 zip → `/parse-json` 时再叠加 base64 化 + `model_dump_json`→`json.loads` 双份峰值。全程无释放点,单请求峰值轻松破 GB。

## 4. P2 — 外围开销

- **legacy 兜底整管线重跑**:解析失败 → 重读源 → 识别 → soffice 转换 → **从提取开始整条管线重跑**,最坏整档解析 2 次 + 一次转换(`serve.py:346-352,427-433`);转换产物 `read_bytes()` 无上限回读(`legacy_convert.py:98`)。
- **表格 geo_ocr 模式**:每张表新建一个 PaddleOCR 引擎并对整页图跑 OCR——同页 T 张表 = T 次整页 OCR + T 次引擎构造,无缓存(`table/_cell_ocr.py:20-24,72-74`);每含表页再渲染 200DPI PNG 串行发送(`table/extractor.py:206-216`)。
- 页眉 `word/header*` **无条件全量解析**,仅取 200 字符进 metadata(`package_reader.py:57-64`、`extractor.py:344-349`)。
- OCR 路 `serve.py` 侧每次解析还多发一次 `GET /api/model-runtime`(`ocr/extractor.py:70-75`)。
- debug 路径:`_DebugTracer` 每 stage 全量 dump 全文档 JSON(`pipeline/base.py:96-151`),仅 debug_dir 开启时。
- `_log` 事件 dict 无条件全程内存累积(`pdf.py:699`、`ocr/extractor.py:123-129`)。

## 5. 修复优先级

| 序 | 改动 | 效果 | 成本 |
|---|---|---|---|
| 1 | `api.py` 端点改 `def` 或解析体 `run_in_threadpool`。**改造时必须 `copy_context().run(...)` 传递 ContextVar,否则 OCR 页级计时静默丢失(见 §6-3)** | 解除服务独占;healthcheck 误报消失(§1 处置 2);部分化解毒 PDF 卡死面 | 一行级 |

| 7 | 页眉解析惰性化(仅正文命中时才回读);`filter_noise` 页码候选先按页分组再比 | 长尾优化 | 小 |

## 6. 遗留 defer 项(计时可观测性,已记台账,不阻塞)

> 背景:`src/document2chunk/timing.py` 是 /parse-pdf 可观测性模块(StageTimer 阶段计时 + stdout 人读 / JSONL 按天滚动双路输出,设计见 `docs/superpowers/specs/2026-09-17-parse-observability-design.md`)。以下三项为该工作流的遗留 defer,已记台账与备忘,列此处仅为与提效改造对齐,避免施工时踩雷。

1. **`_prepare` 快路径耗时不归属阶段**:`serve.py:197` `_prepare`(后缀快路径 + 老格式直转)未包 `timer.stage(...)`,其耗时落在 total 与各 stage 之和的差额里,阶段拆解对不齐。defer:影响仅观测精度,不影响功能。
2. **JSONL 可加 `from_ip`**:`from_ip` 目前仅进 stdout ARRIVE 行(`api.py:369` → `timing.py:114-126`),`StageTimer.__init__` 不接收、`finish()` 的 JSONL record(`timing.py:91-103`)无此字段——按 IP 对账须靠 request_id 回联 stdout。defer:加字段属低价值增强。
3. **线程池改造须 `copy_context()`**:计时器经 `ContextVar`(`timing.py:24` `current_timer`)传递,OCR 页级计时在 extractor 层取 `get_current_timer()`(`ocr/extractor.py:91`)。ContextVar **不自动跨线程**——落实 §5 序 1(解析移线程池)时若直接 `to_thread`/`ThreadPoolExecutor.submit`,新线程里取到的是默认 None,`_timer.ocr_page` 静默 no-op,**页级计时无声丢失且无报错**。必须 `ctx = contextvars.copy_context()` 后 `ctx.run(...)` 执行,或在线程内显式 `set_current_timer`。此项已前置标注在 §5 序 1。

## 7. 效果等价性审查:提效改动是否影响处理结果

> 逐项对照代码审查"改后输出是否与现在一致"。分三档:**A 纯等价**(实现正确则输出逐字节/逐语义一致)、**B 等价但需守卫**(不改解析逻辑,但引入并发后有新风险点)、**C 有输出变化**(本质是契约变更,需决策/对齐)。

| 项(§5 序号) | 档 | 审查结论 |
|---|---|---|
| 1 线程池化 | **B** | 解析逻辑不动,单请求输出不变。但并发暴露 5 处模块级全局(已排查):`_PDF_KIND_DETECTOR`/`_MARKDOWN_FN` 启动期写入(良性)、`_FONT_WARNED` warn-once(良性)、`_writer` 已有锁(`timing.py:156`)、**`_MAGIKA_OBJ` 无锁惰性 init(`format_detect.py:124-129`)→ 并发首请求可能同时构造多个 onnx 模型,需加锁或启动期预热**。另:线程池默认 40 线程,40 个 143MB 解析并发比现在更早 OOM,必须配有界信号量(2-3);ContextVar 需 copy_context(见 §6-3) |
| 2 删 geo + skip_detect | **A**(限 serve 层) | geo 已核实从未使用,删除零影响。路由层 `_pdf_kind`(`api.py:206-221`)与提取器内部检测是**同一确定性判定器**,serve 路径(pages=None)输入相同 → 第二次检测纯冗余守卫,跳过等价。**例外**:提取器带 `pages` 子集时内部检测按子集采样、路由检测按全文,可判定不同,此时守卫是真守卫——所以只能 serve 层构造时传 `skip_detect=True`,**不动 PdfExtractor 库默认值**,对外行为等价 |
| 3 OCR 页级并发 | **B**(并发)+ **C**(部分结果) | 并发本身可做到输出等价,硬约束:`_Idc`(`ocr/_mapping.py:94`)跨页递增发 id(block_000001…),必须**按页序归并后再统一发 id/图片名**(每页块数与串行版相同 → id 完全一致);markdown 导出不渲染 id(`export/markdown.py:27` 仅内部索引)→ zip 模式天然不受影响。跨页后处理(merge_cross_page、页眉页脚)作用于归并后完整序列,与现在相同。**部分结果返回是契约变更**:现在失败=整体 500(Chai 整体重试),改"部分+失败清单"后下游若不检查清单会静默丢页——须与 Chai 对齐或做成选项(默认保持全有全无)。并发会放大 OCR 服务负载("整份 49 页即 500"的同一服务),须有界(4-8)并尊重 429 |
| 4 rels/样式缓存 | **A** | 缓存不可变数据(rels 解析树、(name,ext)、样式链)→ 逐字节等价。唯一坑:**不要连图片 bytes 一起缓存**——现在 bytes 用完即弃,缓存反而推高内存峰值,与目标相悖 |
| 5 MuPDF 看门狗 | **A** | 正常文件零影响(子进程同版本同结果);毒文件从"永久挂死"变"报错",是改善非退化。注意子进程方案冷启动(import+pymupdf 初始化)开销,用常驻进程池摊销 |
| 6 zip 落盘流式 + 去双重序列化 | **A**(语义)/**C**(data 剔除) | zip 改落盘+FileResponse:同 bytes,等价;临时文件须在响应发完后清(FastAPI BackgroundTask)。去掉 `json.loads(model_dump_json())`:语义等价(JSON 消费方无感;字节级空白/转义细节可能微差)。**剔除 `ImageNode.data` 是可见契约变更**:docx 合成图 bytes 目前以 base64 进 /parse-json(pydantic v2 JSON 模式编 base64,`exclude_none` 不排除非 None bytes);Chai 主契约是 /parse-pdf zip 模式不吃此字段,`parse-pdf接口调用文档.md:235` 标注 /parse-json 为"库级接口,供需要结构化树的调用方"——大概率无消费方,剔除前需确认 |
| 7 页眉前缀惰性 + filter_noise 分组 | **A**(按下述实现) | 页眉:输出只有 `metadata.custom["docx"]["header_text"]` 前 200 字符(`extractor.py:344-349`,已核实无任何逻辑消费)。可做**前缀惰性**:逐 header 解析、累积 ≥200 字符即停——join+截断的前缀逐字节一致;须保持 namelist 顺序与非空过滤语义。filter_noise:已读实现(`postprocess.py:304-349`)——内层扫全文档但 `_prov_page(o) != pg: continue` 只比同页,`above_w` 取 max 顺序无关;唯一顺序敏感的是 `candidates` 列表(跨页递增补判按文档序)→ 改"预建页索引+保持原外层遍历序"即等价;若按页分组遍历,candidates 须按(页升序,页内原序)追加 |
